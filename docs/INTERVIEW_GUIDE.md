# 电商运营 AI 工作流：面试讲解手册

这份文档按照真实面试顺序整理。目标不是背诵术语，而是让你能从业务目标、技术实现、问题解决、测试证据和项目边界五个方面讲清楚项目。

## 一、面试开始：请介绍一下你的项目

### 30 秒版本

> 我做了一个基于 FastAPI 和千问的电商运营 AI 工作流。系统先用 Python 工具根据售价、成本、运费和佣金计算真实利润，再把商品资料和工具结果交给模型生成结构化运营策略。模型结果经过 Pydantic 校验、事实边界约束和风险检查，并记录 Token、预估费用、执行轨迹和历史数据。项目还有 Excel 批量分析、47项自动化测试、20条离线案例和 GitHub Actions。

### 60 秒版本

> 我做这个项目的目标不是开发一个能够商业化的电商平台，而是完整实践 AI 应用开发链路。用户在中文网页输入商品卖点、目标用户、售价和成本，FastAPI 接收并用 Pydantic 校验。利润属于确定性计算，所以由 Python 工具完成；模型只负责生成运营建议，并且必须返回固定 JSON。系统再检查高风险营销表达，把结果、执行轨迹、Token 和费用保存到 SQLite，支持历史回放和用户反馈。我使用一条固定案例进行了三次成功的真实模型调用，发现并修复了事实编造和风险误报，并用47项 pytest 和 GitHub Actions做回归验证。

讲完后停下来，等待面试官追问，不要一次把所有细节全部说完。

## 二、为什么做这个项目

推荐回答：

> 我想应聘 AI 应用开发岗位，需要证明自己不仅会调用一次模型 API，还能把模型接入后端业务流程，并处理输入校验、结构化输出、幻觉、异常、成本、数据库和测试。电商运营有明确的利润计算和文案生成任务，适合展示“确定性工具加生成模型”的设计，所以选择了这个场景。

不要回答：

- “这个产品能打败成熟电商平台”；
- “它能明显提升销量和转化率”；
- “已经有客户愿意付费”。

这些说法没有真实数据支持。

## 三、项目完整流程怎么讲

面试官问“整个请求是怎么走的”时，按下面顺序回答：

1. 前端提交商品、卖点、目标用户、平台、价格、成本、运费、佣金和经营目标；
2. FastAPI 路由接收请求，Pydantic 校验字段类型、范围、长度和必填项；
3. Agent 调用 Python 利润工具，计算佣金、总成本、单件利润和利润率；
4. Prompt 服务把用户输入与可信工具结果组合起来，并建立事实白名单；
5. AI 客户端调用千问，要求返回固定 JSON；
6. Pydantic 校验模型是否返回总体判断、定价建议、营销策略、风险提醒和行动计划；
7. 风险服务检查真正的绝对化承诺，同时排除“禁止使用全网最低”这类提醒语境；
8. 系统记录输入、输出、执行轨迹、耗时、Token 和预估费用；
9. SQLAlchemy 将成功结果写入 SQLite；
10. 网页展示结果并允许用户提交“有帮助/需要改进”反馈。

可以画成：

```text
网页 → FastAPI → Pydantic → 利润工具 → Prompt → 千问
→ JSON 校验 → 风险检查 → SQLite → 历史回放与反馈
```

## 四、为什么利润不让大模型计算

推荐回答：

> 利润和佣金是确定性业务规则，同样输入应该得到同样结果。语言模型擅长生成与归纳，但数值计算可能不稳定，所以我把利润计算封装成 Python 工具，再把可信结果提供给模型。这样既降低数值幻觉，也方便单元测试和复用。

可以现场手算示例：

```text
售价：79元
采购成本：35元
运费：8元
佣金率：5%
佣金：79 × 5% = 3.95元
总成本：35 + 8 + 3.95 = 46.95元
单件利润：79 - 46.95 = 32.05元
利润率：32.05 ÷ 79 = 40.57%
```

## 五、为什么叫 Agent

推荐回答：

> 它不是能够自由规划任意任务的通用智能体，而是面向电商运营的可控工作流 Agent。它会理解业务目标、调用利润工具、调用模型、校验结果、执行风险检查并记录轨迹。固定编排是当前阶段的主动选择，因为更容易解释、测试和控制成本。

如果面试官认为它只是 workflow，可以直接承认：

> 是的，从工程分类上它更接近带工具调用的固定工作流。我保留 Agent 名称是为了表达它围绕业务目标完成多步骤任务，但不会把它包装成自主智能体。

## 六、项目遇到的关键问题，以及怎么解决

这是面试最重要的部分。每个问题都按照“现象—原因—方案—结果—边界”回答。

### 问题1：模型返回正确 JSON，但内容会编造

**现象**

第一次真实调用中，模型返回格式完全正确，但自行增加了赠品、20人免费试用、15元获客成本、高铁机场断连和多设备快速切换等输入中不存在的信息。

**原因**

Pydantic 只能验证字段和类型，不能判断自然语言中的事实是否真实；旧 Prompt 虽然写了“不要编造”，但事实边界不够具体。

**解决方案**

1. 将事实限定为用户输入和利润工具结果；
2. 卖点只允许原样引用，不允许推导隐藏能力；
3. 明确写出“蓝牙双模不等于多设备切换”的反例；
4. 新增场景与运营动作必须标记“可选方案”或“需验证”；
5. 禁止新增篇数、预算、金额、周期和体验描述；
6. 模型温度从 `0.7` 降低到 `0.2`。

**结果**

Prompt 1.2 使用相同案例复测后，之前识别出的多设备切换、篇数、具体体验和职场形象效果没有再次出现。

**边界**

只有一条案例完成版本对比，而且 Prompt 与温度同时变化，不能证明所有场景都已解决，也不能判断改善只来自哪个变量。

### 问题2：风险检查把风险提醒本身判为违规

**现象**

模型写的是“禁用绝对化表述”，旧规则因为看到“绝对”两个字，就返回 `needs_review`。

**原因**

旧实现只是简单字符串包含，没有判断词语是在宣传承诺中，还是在否定、禁止和人工复核语境中。

**解决方案**

增加上下文规则：识别“不要、不得、禁止、避免、需要复核”等前后语境。

**结果**

- “商品保证成为销量第一”仍会拦截；
- “禁止使用全网最低”不会误报；
- “不能继续按全网最低宣传”不会误报。

历史记录回放时也使用当前规则重新计算，旧版本保存的误报不会永久保留。

### 问题3：模型调用超时，页面只显示连接失败

**现象**

一次真实测试在30秒处失败，当时所有网络异常都被统一显示为“无法连接大模型服务”。

**原因**

Prompt 变长后，模型响应超过旧超时上限；异常处理没有区分超时、HTTP错误和普通连接错误。

**解决方案**

- 将超时上限调整为60秒；
- 单独捕获 `httpx.TimeoutException`；
- 向用户显示具体超时秒数；
- 只有成功结果才保存进历史记录。

**结果**

下一次相同案例成功返回，耗时37.518秒；Prompt 1.2调用耗时23.183秒。

### 问题4：不知道每次模型调用花了多少

**现象**

早期接口只返回生成内容，无法评估 Token 消耗和调用成本。

**解决方案**

- 解析供应商响应中的 `usage`；
- 记录输入、输出、总 Token 和缓存 Token；
- 单价通过 `.env` 配置；
- 只有价格模型与调用模型完全一致时才估算费用；
- 页面、历史记录和评测报告都展示用量。

**结果**

Prompt 1.2案例记录为847个输入 Token、3,473个输出 Token，总计4,320 Token，本地预估费用 ¥0.0029478。

**边界**

本地估算不等于真实账单，免费额度、缓存、上下文档位和活动价格都可能影响实际扣费。

### 问题5：质量分数看起来专业，但没有真实意义

**现象**

早期版本根据文本长度和行动数量生成自动分数，但这个分数不能代表策略真实质量。

**解决方案**

删除虚假的综合分数，保留可解释的风险规则，并增加用户“有帮助/需要改进”反馈和五维人工评分模板。

**展示的判断能力**

不是功能越多越好。无法解释和没有业务依据的功能应该删除，而不是为了显得复杂而保留。

### 问题6：Windows端口被占用导致启动失败

**现象**

Uvicorn 报 `WinError 10048`，8000和8001被残留进程占用。

**解决方案**

实现 `run_server.py`，通过实际绑定端口判断是否可用，从8000开始自动寻找后续空闲端口，再启动 Uvicorn。

**结果**

演示时不需要手动猜端口，终端会打印实际工作台和接口文档地址。

## 七、如何测试收费的模型接口

推荐回答：

> 自动化测试不能依赖真实模型，否则会产生费用、受网络影响，并且模型输出不稳定。我通过 FastAPI 依赖覆盖注入 Fake AI Client，让它返回固定结构化数据；数据库使用临时 SQLite。真实模型只用于少量固定案例评测，并且命令必须显式添加确认参数。

测试覆盖：

- Pydantic 输入校验和利润工具；
- Prompt 事实白名单与温度；
- AI JSON 解析、超时和供应商错误；
- 风险承诺与提醒语境；
- Token 与费用计算；
- 历史回放和反馈；
- Excel 批量分析与导出；
- 前端静态资源和启动器。

当前共有47项 pytest。GitHub Actions 在每次推送和合并请求时运行同一套测试。

## 八、代码目录怎么讲

```text
app/api/routes/       HTTP接口和错误状态码
app/schemas/          Pydantic输入、输出和AI结构化数据
app/services/         Prompt、模型客户端、Agent、利润、Excel和风险逻辑
app/tools/            可被工作流调用的确定性利润工具
app/models/           SQLAlchemy数据库表
app/repositories/     数据访问层
app/web/              中文网页与交互
evaluation/           20条案例、批量评测、报告和人工评分
tests/                47项自动化测试

```

分层原则：路由层处理 HTTP，service 处理业务，repository 处理数据库，schema 定义数据契约，model 定义数据库表。

## 十、常见追问及回答

### 为什么没有使用 LangChain？

> 第一阶段直接实现 Prompt、HTTP客户端、工具和编排，是为了理解底层调用链，并保持依赖和调试路径简单。当前只有一个确定性工具和固定流程，引入框架收益有限。如果后续出现多工具动态路由、知识库或复杂状态管理，再评估 LangChain。

### 为什么使用 SQLite？

> 当前是本地单用户作品集，SQLite无需额外服务，足以验证ORM、事务、历史和反馈。多用户部署时会迁移 PostgreSQL，并增加迁移工具和权限隔离。

### 为什么不做微服务、Redis和消息队列？

> 当前流量和任务复杂度没有提出这些需求。为了展示技术名词而拆服务会增加运维和一致性成本。我优先完成模型可靠性、评测和测试；只有出现耗时异步任务、重复查询或独立扩缩容需求时才引入相应组件。

### Pydantic能解决模型幻觉吗？

> 不能。Pydantic能验证JSON结构、字段类型和长度，但无法证明自然语言事实正确。事实一致性还需要Prompt边界、检索或工具证据、规则检查和人工评测共同处理。

### 为什么输出Token比输入多？

> 供应商usage可能包含模型生成过程使用的Token，不只等于页面上能看到的文字长度。我按供应商返回值原样记录，并把费用标为本地估算，不自行修改供应商统计。

### API Key怎么保护？

> Key只保存在被Git忽略的本地`.env`。`.env.example`只有字段名和安全默认值；接口只返回是否配置，不返回Key。提交前还会检查暂存区是否含有密钥特征。

### 项目最大的不足是什么？

> 目前只有一条案例完成三个版本的真实模型对比，没有真实店铺商业数据，也没有认证、权限和公网部署。因此它只能证明AI应用工程能力，不能证明提升销量或已经达到生产级。

### 如果投入生产，优先补什么？

> 第一是身份认证、权限和数据隔离；第二是PostgreSQL与数据库迁移；第三是失败调用审计、重试和监控；第四是更大规模人工标注评测；第五才是根据实际流量决定缓存、异步队列和部署架构。
