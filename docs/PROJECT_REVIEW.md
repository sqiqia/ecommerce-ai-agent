# 项目复盘与简历材料

## 先说结论

这个项目适合作为初级 AI 应用开发岗位的作品集，但不应包装成生产级电商系统。

它真正证明的不是“做出了比成熟平台更好的电商文案”，而是完成了一个可运行、可校验、可持久化、可测试的 AI 应用闭环：

```text
业务输入 → 确定性利润计算 → Prompt 构建 → 千问调用
→ 结构化输出校验 → 风险检查 → 历史保存 → 用户反馈
```

对于初级岗位，这条链路可以证明你不只是会在脚本里调用一次模型 API，而是理解如何把模型接进后端应用。

## 简历推荐写法

### 项目名称

电商运营 AI 工作流｜Python / FastAPI / Qwen / SQLAlchemy

### 项目简介

面向电商运营场景开发中文 AI 工作台，将商品利润计算、结构化运营策略生成、Excel 批量处理、历史回放和用户反馈整合为完整应用链路。

### 项目要点

- 使用 FastAPI 与 Pydantic 设计商品分析、AI 文案及 Agent 接口，实现业务参数校验、模型异常映射和 OpenAPI 文档；
- 将 Python 利润计算工具接入固定编排工作流，把可信计算结果注入 Prompt，并校验千问返回的结构化 JSON，降低数值幻觉和格式失控；
- 使用 SQLAlchemy 与 SQLite 持久化请求、运营策略、执行轨迹和用户反馈，支持分页查询及历史详情回放；
- 使用 openpyxl 完成 Excel 逐行校验、批量利润分析和结果导出，并编写 40 项 pytest 测试，通过 Fake AI Client 与临时数据库实现无网络、零模型费用的回归测试；
- 配置 GitHub Actions 在每次推送和合并请求时自动运行测试，公开展示项目的可重复验证能力。

简历空间有限时保留前四条；GitHub Actions 可以并入测试那一条。

## 不要写进简历的内容

- 不要写“提升转化率、销量或运营效率”，因为目前没有真实对照数据；
- 不要写“生产级、高并发、企业级”，因为当前是本地单用户 SQLite 应用；
- 不要写“自主智能体”，当前是可控的固定步骤工作流；
- 不要写 Redis、RAG、微服务、PostgreSQL 或公网部署，除非以后真正实现并验证；
- Docker 配置仍保留在仓库，但作者当前环境没有完成镜像构建验证，因此不作为简历成果。

## 这个项目现在缺什么

最缺的不是更多技术名词，而是业务效果证据。优先级建议如下：

1. 收集 20 到 50 条真实或人工整理的商品案例，建立固定输入、风险点和人工评价；
2. 用同一批案例比较 Prompt 或模型版本，统计结构合格率、风险命中率和人工“有帮助”比例；
3. 保存失败调用的错误类型和耗时，形成基础运行统计；
4. 再考虑做一个可访问的演示环境；
5. 只有拿到商品知识、平台规则或客服资料时再做 RAG；只有出现耗时任务和重复查询时再引入 Redis；当前规模不适合拆微服务。

完成第 1、2 项后，简历才能出现真实数字，例如“在 30 条固定案例上结构合格率为 96%”。在实际测量前不要提前填写任何数字。

## 60 秒介绍

> 我做了一个电商运营 AI 工作流。系统先用 Python 根据售价、成本、运费和佣金计算利润，再把商品信息、经营目标和计算结果交给千问生成固定 JSON 格式的运营策略。返回结果经过 Pydantic 校验和高风险营销词检查，然后使用 SQLAlchemy 保存请求、结果、执行轨迹和用户反馈。项目还支持 Excel 批量分析。我使用 Fake AI Client 和临时数据库编写了 40 项自动化测试，并通过 GitHub Actions 在每次推送时回归验证。这个项目目前是本地作品集，不把它包装成生产系统。
